\title{Booting a Bootstrapped Operating System Entirely Written by AI}
\author{Martin Monperrus}

\begin{document}
\maketitle

\begin{abstract}
We report on \sysname{}, an x86 operating system in which every line of code, from the
boot sector to the compiler that builds it, was written by Claude working as a coding
agent. \sysname{} boots in QEMU through its own two-stage boot loader into a 32-bit
kernel with a disk driver, a file system, a shell, a scripting language, and a compiler
to an in-kernel bytecode VM. Its build uses no third-party compiler, assembler or linker:
the agent wrote its own, and bootstrapped them until the second and third self-compiled
generations were byte-identical. The human set the goals and wrote no code. From plan
approval to a working OS with both languages took \plantoosmin{} minutes. The toolchain
took \tcactivehours{} hours of agent activity and accounts for \nttoolchain{} of the
\ntproduct{} defects that the transcript shows the agent finding and fixing, half of
which no commit message mentions.
\end{abstract}

\section{Introduction}\label{sec:intro}

Power on the machine. A 512-byte boot sector loads a kernel, the kernel mounts its file
system, and a shell prompt appears. Compile a program, run it. Type \texttt{play}, and a
battle screen in the style of a Game Boy Advance lights up. No human wrote a single line
of it: not the boot sector, not the kernel, not the game, and not the assembler, C
compiler and linker that built all of them, which also built themselves. An AI did.

Coding agents are usually judged on changes to code that already works, from single
functions~\cite{chen2021codex} to repository-level issue fixing~\cite{jimenez2024swebench}.
Writing a system from an empty repository is a different task. The agent has to choose
an architecture, keep it coherent over thousands of lines, and debug failures whose only
symptom may be a machine that prints nothing. An operating system is the extreme case.
Below the kernel there is no runtime to report a mistake: a wrong descriptor table entry
resets the machine, and an I/O instruction with the wrong operand size corrupts the disk
without a word. Unix~\cite{ritchie1974unix} and xv6~\cite{cox2006xv6} show how much a
small kernel can do; they also took skilled people to write.

There are precedents for agents building large systems from nothing. A team of 16 Claude
agents wrote a C compiler that builds Linux, but it relies on GCC's assembler and
linker~\cite{carlini2026ccc}. Hundreds of agents built a web browser in a
week~\cite{lin2026scaling}. A month before this work, Claude Fable 5 wrote the core of an
NT-style kernel in Rust, with a scheduler and a memory manager, that boots in
QEMU~\cite{suiche2026ntoskrnl}. All of them are compiled by existing, human-written
compilers (GCC, \texttt{rustc}), so every instruction that runs was chosen by a code
generator no agent wrote. To the best of our knowledge, no one has reported a
bootstrapped operating system written by an AI: one where the AI wrote not only the OS
but also the assembler, compiler and linker that build it, where that toolchain compiles
itself to a byte-identical fixed point, and where it is the only toolchain that ever
compiles the OS. \sysname{} is such a system.

\paragraph{Methodology.} One human gave one Claude Code agent (\sessionmodel{}) a goal
and an empty repository, and let it work in a single session. The human set goals,
answered the agent's questions and said ``go'', but wrote no code. We study two
artifacts: the git history of the
system\footnote{\url{https://github.com/monperrus/boot-to-claude}, commit \ospin{}.} and
the complete transcript of the
session,\footnote{\url{https://github.com/monperrus/boot-to-claude-paper}} with every
prompt, model response, tool call and tool output. Every number in this paper is computed from these two sources by a script,
including how often the agent ran each oracle and how often the oracle said no.

\paragraph{Results.} \sysname{} boots through its own boot loader into a kernel with a
file system, a shell, a scripting language and a compiler to bytecode. Its assembler, C
compiler and linker were written by the agent and compile themselves to byte-identical
binaries. From plan approval, the OS with both languages took \plantoosmin{} minutes;
the toolchain took \tcactivehours{} hours of agent activity. The agent ran its
scripted oracles \noraclesruns{} times and saw \noraclesfailed{} failures, most of them
while switching the build to its own toolchain. The transcript records \ntproduct{}
defects found and fixed in the system, \nttoolchain{} of them in the toolchain; only
\ntreported{} appear in a commit message.

\paragraph{What we learned.} Beyond this one build, the experiment yields knowledge that
carries over to other agents and other systems:
\begin{itemize}
  \item \textbf{An agent is as good as its oracles.} The agent worked in a loop: change
        the code, run an oracle, iterate until it passes. A defect that its oracle could not
        see stayed in until another oracle did (Section~\ref{sec:oracles}).
  \item \textbf{Most defects are silent.} \ntsilent{} of the \ntproduct{} product defects
        produced no error message at all. An oracle that waits for an error misses them; agentic workflows
        have to state the expected output and compare (Section~\ref{sec:defectlist}).
  \item \textbf{The whole system is the best test program.} Booting the OS caught
        toolchain defects that no unit test covered, because the unit tests cover only what
        the agent thought of.
  \item \textbf{The agent's oracles have defects too.} \ntoracle{} defects were in the
        oracles themselves, and the worst of them made an oracle report success after a
        failure. Oracle design is essential (Section~\ref{sec:guidelines}).
  \item \textbf{The toolchain is harder than the OS.} \nttoolchain{} of the \ntproduct{}
        product defects were in the assembler, compiler and linker. Removing the last
        human-written tool from the build was most of the work.
\end{itemize}

\paragraph{Contributions.}
\begin{itemize}
  \item \textbf{The first bootstrapped operating system written by an AI}, to the best of
        our knowledge. \sysname{} has its own boot loader, kernel, file system, shell and
        two languages, and its own assembler, C compiler and linker, which compile
        themselves to a byte-identical fixed point and are the only tools that build the
        OS. No line of the stack was written by a human.
  \item \textbf{One agent, one session, no human code.} Where comparable systems used
        teams of 16 to hundreds of agents~\cite{carlini2026ccc,lin2026scaling}, a single
        agent wrote \sysname{}. The OS with both languages took \plantoosmin{} minutes
        from plan approval; the full toolchain, \tcactivehours{} hours of agent activity.
  \item \textbf{The oracle, not the code, is what makes it possible.} We show from the
        transcript that the agent was only as good as its oracles: it ran them
        \noraclesruns{} times, they rejected its work \noraclesfailed{} times, and the
        most telling defects were silent ones that only an oracle booting the whole
        machine caught.
  \item \textbf{A fully transparent open-science package.} We release the system's
        source and history, the complete transcript of the session that built it, with
        every prompt, model response, tool call and tool output, and the scripts that
        recompute every number, table and figure in this paper from them. Anyone can
        check every claim we make, down to the individual tool call: the phases,
        prompts, oracle runs and defects in this paper are hyperlinks into the rendered
        transcript.\footnote{\url{\siteurl}}
  \item \textbf{A game written by an AI, for an AI}, on a stack written by an AI from the
        boot sector up.
\end{itemize}

\section{Goal}\label{sec:goal}

\paragraph{Total AI authorship.} We aim at total AI authorship of a computing system: every line of
code, in the system and in everything that builds it, is produced by an AI coding agent.
We use a coding agent to generate this computing system.
We decompose this goal into three claims.
\begin{description}
  \item[Full AI-written kernel.] No line in the kernel is written by
        a human or taken from an existing project.
  \item[Full AI-written stack.] No line in the build system (compiler, linker) is written by
        a human or taken from an existing project. We do not use a third-party compiler.
  \item[Full bootstrap.] The system is AI-bootstrapped. An AI-written toolchain (compiler, linker) builds the AI-written OS and builds itself.
\end{description}

The agent in this study is Claude, but this is incidental; the question is whether
total authorship is achievable by an AI agent at all. 

\paragraph{Rationale for the bootstrap.} An OS whose source was written by AI but which \texttt{gcc}
compiles is still a joint work: every machine instruction that runs was chosen by a code
generator written by humans. The bootstrap removes that dependency. The host compiler is
used once, to produce a first binary of the AI's compiler; from then on the AI's compiler
compiles itself, and the fixed point shows that the result no longer depends on the human-written
compiler. The bootstrap is also a strong oracle in its own right: a
compiler that compiles its own source correctly has to handle a real, large C program.

\paragraph{Two compounding difficulties.} We have two hard problems. The first is
writing an operating system: code that runs on bare hardware, with no runtime underneath, where
a mistake resets the machine or corrupts data without a word. The second is writing a compiler
strong enough to compile both that operating system and itself. 
Building a C compiler is
hard even with the abundant resources of Anthropic: their team of 16 agents spent about \$20{,}000
on a C compiler that builds Linux, yet, they still relies on GCC's assembler and
linker~\cite{carlini2026ccc}. 

The two difficulties
compound. When the OS misbehaves after bootstrap, the cause may be in the OS or in the compiler that
built it, and the symptom cannot tell them apart. An \texttt{in} instruction encoded without its
operand-size prefix, for example, showed up as a corrupted file system
(see Section~\ref{sec:defectlist}).

\paragraph{Scope.} The target is a complete, if small, computing system: one that boots
on a bare machine and that lets a user write and run programs in
languages of its own. Concretely, a boot loader, a kernel, a file system, an interactive
shell, an interpreted scripting language, and a compiled language. Then the tools that build all of it: an assembler, a C compiler and a linker.
Table~\ref{tab:goal} sums up what is required of each part.

\section{\sysname}\label{sec:system}

\paragraph{Boot and kernel.} The BIOS loads a 512-byte boot sector, which loads a second
stage. The second stage enables the A20 line, loads the kernel, installs a flat GDT and
switches to 32-bit protected mode. The kernel owns its GDT and an IDT that covers CPU
exceptions only. It has a free-list allocator over a fixed 1\,MB heap, VGA text and
COM1 serial output, a polled ATA PIO disk driver, and a polled PS/2 keyboard driver.

\paragraph{Deliberately single-tasking.} The kernel never enables interrupts after boot.
It has no scheduler, no paging and no user mode. The shell and both language runtimes run
in kernel context.

\paragraph{Above the kernel.} \emph{tinyfs} is a flat file system with a superblock, a
free-block bitmap, a fixed inode table and 4\,KB maximum file size. Its format code is
compiled twice, once into the kernel and once into the host tool that formats the disk
image, so there is a single implementation of the on-disk format. The shell offers
\texttt{ls}, \texttt{cat}, \texttt{write}, \texttt{rm}, \texttt{run}, \texttt{build} and
\texttt{exec}. \texttt{run} executes a dynamically typed script with a tree-walking
interpreter. \texttt{build} compiles a statically scoped, integer-only C-like language to
stack bytecode, and \texttt{exec} runs it in a VM that supports recursion. The shell's
\texttt{play} command starts a game, described in Section~\ref{sec:game}.

\paragraph{The \sysname{} toolchain.} Three tools replace \texttt{nasm}, \texttt{gcc},
\texttt{ld} and \texttt{objcopy}:
\begin{itemize}
  \item an \emph{assembler} for the subset of NASM syntax that the OS's assembly files
        and the compiler's output use, with no macro preprocessor. It writes either a
        flat binary (the boot sectors) or an ELF32 relocatable object;
  \item a \emph{C compiler} for tinyC, a C dialect scoped to what the code base needs:
        \texttt{\#include} and constant \texttt{\#define} only, structs, unions, enums
        and function pointers, no type wider than 32 bits. It emits assembly text for the
        assembler, either freestanding for the kernel or as a static Linux program that
        calls the kernel directly through system calls;
  \item a \emph{linker} that merges ELF32 objects, applies the two x86 relocation types
        the assembler produces, and writes either the flat kernel image or a static
        Linux executable. Writing the flat image itself made \texttt{objcopy}
        unnecessary.
\end{itemize}
A minimal C library (unbuffered \texttt{FILE} I/O, a bump allocator, a subset of
\texttt{printf}) lets the toolchain's own source, which uses ordinary libc calls, be
compiled by the toolchain. Table~\ref{tab:size} gives the size of each part.

\paragraph{Bootstrap path.} The toolchain is written in C, so its very first binary has
to come from a compiler that already exists. The host C compiler (\texttt{gcc} by
default, any C compiler will do) is used exactly once, to build Stage~1 of the
toolchain from its source. Stage~1 then compiles the same source into Stage~2, and
Stage~2 compiles it again into Stage~3. Let $S_i$ be the binaries of stage $i$. The
bootstrap is accepted only when
\begin{equation}\label{eq:fixpoint}
  S_2 = S_3 \quad \text{byte for byte, for each of } \texttt{as},\ \texttt{cc},\ \texttt{ld}.
\end{equation}
Equation~\eqref{eq:fixpoint} shows that the compiler compiles itself to the same result
it was compiled to, so the bytes of Stage~2 come from the toolchain's own code
generator, not from the host compiler's. Stage~2 then
builds the boot loader, the kernel and the disk-image tool; the host compiler never
compiles any of them. The emulator, \texttt{qemu-system-i386}, stays external: it is the
machine \sysname{} runs on, not part of what builds it.

\subsection{Tiny Monsters}\label{sec:game}

% design and implementation
Now that we have a working operating system,  we implement and play with a Pokemon like game.
The result, \emph{Tiny Monsters}, is the most visible demonstration of the full AI-written
stack. Every pixel in Figure~\ref{fig:battle} is drawn by code Claude wrote, compiled by
the compiler Claude wrote, on a kernel Claude wrote.


\begin{figure}[h]
\centering
\includegraphics[width=\textwidth]{fig/battle.png}
\caption{Tiny Monsters running on \sysname{} in QEMU, four frames from the agent's own
screencast. Top left: choosing a starter. Top right: a mirror match, Emberpup against a
wild Emberpup. Bottom: Fire beats Grass; Flame Burst takes the wild Leafling down until

\paragraph{Rules.} Three species, Emberpup, Aqualing and Leafling, one per type in a
rock-paper-scissors cycle: Fire beats Grass, Grass beats Water, Water beats Fire. A move
with the type advantage does 1.5 times its damage, one against it half. The player picks
a starter and meets wild monsters whose HP grows with each win. HP does not regenerate,
and five wins make the player Champion.

\paragraph{Made for a machine player.} Until then the kernel only read the keyboard; the
serial port was output only. The agent added serial input and made the shell and the
game poll both sources (\inputlines{} lines in \texttt{input.c}), so a human at the
keyboard and a program on the serial line can drive the same session interchangeably.
The game speaks a plain text protocol: it prints the screen as text, and reads a digit,
\texttt{run} or \texttt{quit}. Playing found a \defect{D-C09-01}{real bug}: the random move
picker took a modulo of a 32-bit value with the sign bit set, which \sysname{}'s compiler
only supports as signed division, and read a garbage move name with absurd damage.

\paragraph{A graphical battle screen.} Asked next for \emph{``a good looking GUI like
Pokemon Ruby on GBA''}, the agent wrote a driver for VGA mode 13h (320$\times$200, 256
colors) that programs the video card's registers directly, without BIOS calls
(\vgadriver{} lines), and a bitmap font of its own design (\fontlines{} lines). The three
monsters are not images: \texttt{sprites.c} draws them from filled circles, ellipses and
triangles in \gamesprites{} lines. The battle scene, with sky, ground, platforms, HP bars
and a dialogue box, takes \gamegui{} lines on top of the \gamerules{} lines of game
logic. The graphics are purely additive: the text sent over serial is byte for byte the
same, so the machine player sees no difference. Returning to the shell restores text
mode, which took a debugging session of its own because \defect{D-C09-05}{mode 13h
overwrites the video memory plane} where the text font lives.

\paragraph{Built by AI, played by AI.} The game was designed for an AI player from the first
request (\emph{``a Pokemon like game such that an AI agent later plays over serial port''}),
and its first player was Claude itself. Before the human saw the game, the serial game
test that the agent wrote along with it had already fought full battles over the serial
port (Table~\ref{tab:oracles}). When asked to play for five minutes, the agent booted the
OS without a display, wrote a player that connects to QEMU's serial socket, and played
\playruns{} runs in \playseconds{} seconds, restarting after each faint, with no human and no
keyboard in the loop. 


\subsection{Process Metrics}\label{sec:history}

The work happened in one Claude Code session using \sessionmodel{}, with
\nassistant{} model responses and \ntoolcalls{} tool calls, of which \nbash{} shell
commands and \nedit{} file writes or edits. The context window filled up and was
summarized \ncompactions{} times. Table~\ref{tab:phases}, in the appendix, splits the session at each phase commit. Of the \ncommits{} commits in the repository, all but two were committed by
the agent. The other two are the initial empty commit and a ten-line Makefile target for
running QEMU with a display. The agent wrote that target in response to the human's
report that typing showed nothing, and the human ran \texttt{git commit}.

\paragraph{The toolchain over four days.} Replacing the host tools took
\tcactivehours{} hours of agent activity, about nine times the OS. The assembler had to
grow from the instructions in four hand-written \texttt{.S} files to everything the C
compiler emits. The kernel source was first rewritten into the tinyC dialect while still
building with \texttt{gcc} (phase T3), so that each change could be checked as
behavior-preserving before the new toolchain was in the loop.

\paragraph{The fixed point.} Phase T8 implemented the bootstrap path and reached
Equation~\eqref{eq:fixpoint}. Compiling the toolchain with itself required features it
had never needed for the kernel: variadic functions, multi-dimensional arrays, and the
minimal C library.

\section{Defects}\label{sec:defectlist}

This section describes the defects the agent made and how they came to light;
Section~\ref{sec:oracles} then describes the oracles that revealed them. The defects matter
for the auditability of an agent, to anyone who reviews such a system: if a defect leaves
no trace in the history, a reviewer who reads only the commits cannot see what the agent
got wrong.

\subsection{Method.} Commit messages report the defects the agent chose to mention. To
see all of them, we cut the transcript into ten chunks at phase boundaries and had ten
annotator agents list every defect the agent encountered from commit analysis: what was wrong, the tool call
whose output first showed it, the edits that fixed it, the check that confirmed the fix,
and the commit message that reports it, if any.

Each quotes its evidence
verbatim. A script then checked every cited tool call against the transcript and every
quote against the chunk. 
\href{\siteurl/defects.html}{All records} are on
the verification site, each with its type (product, oracle tooling, environment), its
component, the quote, and links to the tool calls that showed, fixed and
confirmed it.

\subsection{Results.} The transcript holds \ntdefects{} defects: \ntproduct{} in
\sysname{} itself, \ntoracle{} in the oracle tooling, and \ntenv{} in the environment
(Table~\ref{tab:defects}).

\ntreported{} of the \ntproduct{} product defects are
reported in a commit message; the other \ntunreported{} were found and fixed between
commits and left no trace in the commit history, they are visible only in the trajectory. The toolchain accounts for \nttoolchain{} of
the \ntproduct{}, the C compiler alone for \ntcc{}: building a compiler strong enough
was the harder half of the task. \ntmultiattempt{} defects took more than one failing
check to fix, up to \ntmaxattempts{}. 

\input{gen/tab-defects}

\paragraph{What revealed them.} \ntbuildrevealed{} product defects showed up at build
time, mostly the compiler rejecting C it did not yet support. \ntbootrevealed{} were
caught by an oracle that boots the machine, and \ntsilent{} had a silent symptom: wrong
output, a hang, corrupted data or a wrong picture, with no error message. \ntcodereading{}
were found by the agent reading its own code, typically while investigating a nearby
failure. Three patterns show why the end-to-end oracles mattered.

\paragraph{Many defects were silent.} Silent means that the defective component reported
nothing: no compiler error, no assembler warning, no CPU exception. The machine kept
running, and the defect showed up later, elsewhere, as wrong behavior. An
\defect{D-C06-04}{\texttt{in}/\texttt{out} instruction} encoded without its operand-size
prefix read two 16-bit words per access instead of one, which surfaced as file system
superblock corruption. The compiler's lexer had \defect{D-C06-13}{no case for the
\texttt{\textbackslash b} escape} and read the backspace character literal as the letter
\texttt{b}, so every typed \texttt{b} in a shell command acted as a backspace. In the
scripting interpreter, \defect{D-C01-08}{integer addition} fell through to a default
branch returning 0, so \texttt{i = i + 1} looped forever. All three were caught by the OS
system test, because it compares what the machine prints with what it should print: the
self-test reported failing file system checks, the echo of a typed \texttt{build} came back
as \texttt{uild}, and the test timed out waiting for the line \texttt{x = 14}. The
exception handlers, which catch crashes, saw none of them. The take-away: an oracle that
only waits for an error message misses most defects; it must state the expected output and
compare.

\paragraph{Defects hid behind other defects.} A \defect{D-C04-12}{three-operand
\texttt{imul}} that dropped its immediate went unnoticed because code that wrote and read arrays used the same wrong
index formula, so the errors cancelled. It surfaced only when a host program built by the agent's
compiler, assembler and linker read \texttt{argv}, an array written by the Linux kernel, and
failed to open its input file. The take-away: a test in which the same code writes and
reads the data checks that the code agrees with itself, not that it is right. Such
defects show only where the data crosses into code the agent did not write, or is checked
against a value computed independently.

\paragraph{The system test caught what unit tests missed.} The assembler's
\defect{D-C08-08}{\texttt{.dq} directive} computed its high 32 bits with a shift by 32, which x86 masks to a
shift by 0. No toolchain test used \texttt{.dq}. The boot loader's disk address packet
does, and only the OS system test caught it: the machine never got past the boot sector.
The take-away: unit tests cover what their author thought of, and here the author is the
agent that wrote the bug. The real product exercises what it actually uses. Fast unit
tests do not replace the end-to-end test; they make it the last line, not the only one.

\subsection{Defects in the oracle loop}\label{sec:oracledefects}

The oracles are code too and \ntoracle{} of the defects were
in them. They differ in nature from product defects: a product defect makes the oracle
say no, while an oracle defect makes it say the wrong thing, or nothing. Three kinds
appear.

\paragraph{Oracles that could not fail.} The toolchain test runner
\defect{D-C03-18}{had no expected exit code} for one fixture, so that test was silently
skipped. The \defect{D-C04-13}{pointer test kept passing} with the broken three-operand
\texttt{imul}, because it wrote and read arrays with the same wrong index formula. Worse,
\defect{D-C04-17}{ad-hoc verification commands} printed success lines such as
\texttt{IDENTICAL} after a step had already failed, and misled the diagnosis. A
false \texttt{PASS} is the most dangerous output an oracle can produce, because the agent
trusts it. None of the three was caught by an oracle. The skipped fixture was visible
only because the runner printed a \texttt{SKIP} line, and the agent registered the
missing expected value. The other two were found by the agent reading the output against
itself: an error line directly followed by a success line. For the ad-hoc commands, the
agent reran each step on its own with its exit code printed. The weak pointer test,
found while chasing the \texttt{imul} defect, was never strengthened.

\paragraph{Oracles that could not observe.} A \defect{D-C09-03}{QEMU serial socket} in
\texttt{server,nowait} mode discards everything the guest prints before a client
connects, so a script waiting for the boot banner timed out on a healthy machine. A
\defect{D-C10-06}{screencast recorder} assumed 320$\times$200 frames where QEMU produces 640$\times$400, and
the agent first blamed a torn file read. Both were caught by their symptom only: the
script waited for a banner that a healthy machine had already printed, and the frames,
looked at by the agent, were sheared and double-exposed. Neither symptom points at the
instrument, so the agent first suspected the system or the wrong part of the
instrument. A stricter re-read, its first fix for the recorder, rejected every frame and
produced an empty video. Each time, the agent had to debug its instrument before it could
trust it again.

\paragraph{Oracles that killed themselves.} \defect{D-C10-05}{Several commands} killed
leftover QEMU processes with \texttt{pkill -f} and a pattern that probably also matched the
command line of the shell running it, so the shell died and the test never ran. The
symptom, exit code 1 with no output at all, looks exactly like a failing system. The agent
noticed only after repeated runs that printed nothing, not even the test's first line.
It never fixed the cause: it worked around it by running \texttt{pkill} and the test in
separate tool calls.


\section{Oracles for Coding Agents}\label{sec:oracles}

A coding agent is as strong as the oracles it uses. The agent proposes a change, the oracle
judges it, and the agent iterates until the oracle agrees. The outcome quality depends on the oracle: a weak one lets defects through, a missing
one leaves the agent guessing.
Oracles
serve twice in the loop: they reveal a defect, and they confirm its fix.

\sysname{} had strong oracles, listed in
Table~\ref{tab:oracles}, and the agent consulted them constantly: it ran the four
scripted ones \noraclesruns{} times, and \noraclesfailed{} of those runs failed. 
\href{\siteurl/oracles.html}{Every run} is listed on the verification site with the
defects it revealed and the fixes it confirmed, and every defect links back to the oracle
that found it: \ntfirstinrun{} of the \ntdefects{} defects were first seen in a scripted
oracle run, and \ntconfirmedinrun{} fixes were confirmed by one.

\subsection{Three kinds of oracle}\label{sec:oraclekinds}

The oracles of Table~\ref{tab:oracles} decide correctness in three different ways, which
differ in what they need to exist beforehand.

\paragraph{Expected-output oracle.} The test states what the system must produce for a
given input, and compares. The OS system test compares the serial console with the
expected text of each shell session, the toolchain tests compare the exit code of each
compiled program with a registered value, and the boot self-test checks each result
against an expected value. It needs someone, here the agent, to know the right answer in
advance, and it checks only what that someone thought of.

\paragraph{Differential oracle.} The same input goes through the system and through a
reference implementation, and the two outputs must agree. During the transition the
old tools were still available: the kernel was first rewritten into the tinyC dialect
while still building with \texttt{gcc}, so the OS test could confirm each rewrite before
the new compiler was in the loop, and the linker's flat output was compared byte for
byte with \texttt{objcopy}'s. It needs no expected value, but it needs a reference, and
here the goal was to remove the references from the build.

\paragraph{Fixed-point oracle.} The system is applied to itself, and the result must not
change: the toolchain compiled by Stage~1 and by Stage~2 must be byte-identical
(Equation~\eqref{eq:fixpoint}). It needs neither an expected value nor a reference, which
is why it took over once the old tools were gone. It is also the weakest of the three on
its own: a compiler that consistently miscompiles a construct its own source never uses
still reaches a fixed point.

\subsection{How the oracles observe and decide}\label{sec:oracleobserve}

\paragraph{Single observation channel.} Every expected-output oracle that runs the OS
compares the same thing: the text on the serial console. The kernel writes every line of
output twice, to the VGA screen and to the COM1 serial port. Even a crash is written:
the CPU exception handlers print the number of the faulting exception to the serial port
before halting the machine. The oracles run QEMU without a display and save everything
the serial port receives to a file, which the agent reads. With this design, a crash, a
hang and a wrong answer all are text the agent can compare with the expected output. The
agent built this channel in phase 0, before there was anything to test, and kept it for
six days.

\paragraph{Binary verdicts.} Each scripted oracle, of whichever kind, ends with one line,
\texttt{PASS} or \texttt{FAIL}: the expected-output comparison matched or not, the
differential comparison agreed or not, the fixed point was reached or not. There is
nothing to interpret. When a run produces neither, because the machine hung until the
timeout, the tool under test crashed, or the build broke first, the absence of
\texttt{PASS} is itself the failure.

\subsection{How the kinds combine}\label{sec:oraclecombine}

\paragraph{The kinds in time.} The three kinds took turns over the session.
Expected-output oracles ran throughout. Differential oracles ran while the old tools were
still in the build, until the build switched over to the new toolchain (phase T7). The
fixed-point oracle took over in phase T8, when the bootstrap removed the last reference.
Switching the build over is where the oracles mattered most: \ntsevenfailed{} of the
\noraclesfailed{} failing oracle runs of the whole session happened in phase T7 alone.

\paragraph{End to end.} The OS system test is an expected-output oracle on the whole
system. It boots the boot loader and kernel built by the toolchain under test, and drives
them as a user would. Any defect anywhere on that path, in the assembler's encoding, the
compiler's code generator or the linker's relocations, shows up as a wrong line on the
serial console. It also covers the gap of the fixed-point oracle: a toolchain that
reaches its fixed point while miscompiling something the OS uses still fails the OS
system test. This is what made the toolchain safe to replace: the OS itself is the
largest test program the toolchain can be checked on.

\paragraph{Fast and slow expected-output oracles.} The toolchain tests and the OS system
test are expected-output oracles at two scales. The toolchain tests run
\ntoolchainfixtures{} small programs on the host in seconds; the OS test boots a machine.
The agent ran them \ntoolchaintestruns{} and \nostestruns{} times respectively, iterating
on the fast oracle and confirming on the slow one.

\paragraph{Regression tests.} When a failure of the slow oracle exposed a defect, the
agent added a regression test for its class, turning the defect into one more expected
output of the fast oracle.

\subsection{Guidelines for Oracle Design}\label{sec:guidelines}

The defects of Section~\ref{sec:defectlist}, in the product and in the oracles, and the
oracles of Section~\ref{sec:oracles} suggest the following guidelines
for designing oracles for coding agents. 

\begin{enumerate}
  \item \textbf{Combine the three kinds of oracle} of Section~\ref{sec:oraclekinds}. An
        oracle that only waits for an error misses silent defects: state the expected
        output and compare. Code that writes and reads its own data agrees with itself
        even when wrong: check it against a reference implementation while one exists,
        against code the agent did not write (the Linux kernel, the BIOS), or, once no
        reference is left, against itself with a fixed point.
  \item \textbf{Instruct the agent to write and run system tests, end to end.} They are
        excellent at finding failures. The unit tests cover what the agent thought of;
        the whole system exercises what it actually uses. Here the test that boots the
        OS caught defects that no toolchain test covered (Section~\ref{sec:defectlist}).
  \item \textbf{Derive one verdict from exit codes, never from printed text.} A step that
        prints a success line unconditionally lies after a failure. A missing verdict, a
        hang or a crash of the harness, counts as a failure
        (Table~\ref{tab:oracles}, \emph{No verdict}).
  \item \textbf{Validate the instrument on a healthy system.} When a check fails, first
        ask whether the instrument can observe at all: capture from the start, check frame
        sizes, run it once on a known-good build.
  \item \textbf{Keep the test harness out of its own way.} By test harness we mean the
        scripts and commands the agent writes to start, drive and stop the system under
        test, here QEMU, not the coding agent's harness (Claude Code). The two meet,
        though: the test harness runs inside the shell of the agent's tool calls. A
        cleanup that matches processes by a pattern can match that shell and kill the
        test run with it, which looks exactly like a broken system. Clean up by process
        id, and keep sockets, timeouts and cleanup in the test harness, never mixed
        with the step under test.
\end{enumerate}

\section{Threats to Validity}\label{sec:threats}

The defect analysis relies on annotator agents reading the transcript. They may have
missed defects or misjudged a cause; we mitigated this with verified verbatim
evidence, an automatic check of every quote and tool call, a coverage check against
the commit messages, and a manual check of a random sample. 

Oracle verdicts are read from the transcript by matching each
script's \texttt{PASS} and \texttt{FAIL} lines. A run counts only when a shell command
executes the oracle's script; a single test case run by hand does not, so the run counts
are a lower bound.

Active time is
estimated from transcript timestamps, counting gaps shorter than ten minutes; a long
build without output would be counted as idle. This is one session with one model, so
it shows that the result is possible, not how often it happens. Finally, the system runs
on QEMU only; real hardware is less forgiving.

\section{Related Work}\label{sec:related}

\paragraph{Complex systems built by coding agents.} Since 2025, practitioners have
reported coding agents building systems far beyond single features, mostly in blog posts
rather than papers. The closest to \sysname{} is Anthropic's C compiler~\cite{carlini2026ccc}:
16 parallel Claude Opus 4.6 agents, nearly 2{,}000 sessions and about \$20{,}000 produced a
100{,}000-line Rust compiler that builds Linux 6.9 for three architectures. It has no
assembler or linker of its own and calls GCC for 16-bit x86 code.
%% Key difference
\sysname{} owns its assembler, compiler and linker and reaches a self-hosting fixed point. 

% cursor
Cursor ran hundreds of
agents for about a week in a planner, worker and judge hierarchy to build FastRender, a
web browser of over a million lines~\cite{lin2026scaling}. Huntley ran Claude in a loop
with a single prompt for three months and obtained \emph{cursed}, a programming language
with an LLVM back end~\cite{huntley2025cursed}. Stenström built JustHTML, an HTML5 parser
that passes the 9{,}200 tests of html5lib-tests, and reports the lesson this paper also
draws: a complete test suite is what lets the agent measure its own
progress~\cite{stenstrom2025justhtml}. All three systems are turned into running code by
tools written by humans, such as LLVM for \emph{cursed} and the Python interpreter for
JustHTML; \sysname{} is the only one in which the agent also wrote, and bootstrapped, the
tools that build it.

Closest in domain, Suiche
reports that Claude Fable 5 wrote the core of \texttt{ntoskrnl-rs}, an NT-style x86-64
kernel in Rust that boots in QEMU and passes its self-tests. ~\cite{suiche2026ntoskrnl}. As a kernel it is more ambitious than
\sysname{}'s: it has a scheduler, a memory manager with page tables, and interrupt-driven
timers, and later work ran unmodified Windows drivers and programs. But it is a Rust
project compiled by \texttt{rustc}, and its core has no file system, shell or user
programs. What set \sysname{} apart is a whole stack from boot sector to a
self-hosted toolchain with no third-party compiler left in the build.

\paragraph{Benchmarks for building from scratch.} HumanEval~\cite{chen2021codex} measures
function-level synthesis, and SWE-bench~\cite{jimenez2024swebench} measures issue
resolution in existing repositories. Commit0~\cite{zhao2025commit0} asks agents to
implement 54 Python libraries from a specification and unit tests. ProjectEval~\cite{liu2025projecteval}
and ProjDevBench~\cite{lu2026projdevbench} evaluate whole projects generated from natural
language requirements. In all of them the oracle is given to the agent. In \sysname{} the
agent wrote its oracles too, as it would be done in the real world (Section~\ref{sec:oracles}).

\paragraph{Agents that play games.} In Claude Plays Pokémon, Claude plays Pokémon Red
through an emulator, reading the screen and pressing buttons~\cite{techcrunch2025pokemon}.
Tiny Monsters reverses the setup: the agent wrote the game, the OS under it and the
toolchain that built both, and designed a text interface over the serial port so that an
agent can play without reading pixels.

\section{Conclusion}\label{sec:conclusion}

A language model wrote a small, single-tasking operating system, then wrote the
assembler, compiler and linker that build it, up to a byte-identical self-hosting fixed
point. The human set goals and said ``go''. The OS was the easy part. Most of the effort
and most of the defects went into the toolchain, and most defects were found by booting
the machine.

Beyond the system, the experiment teaches how such a system gets built. The agent was as
good as its oracles. Most of its defects were silent, so the oracles had to compare
against expected output, and the strongest oracle was the whole system booting. The
oracles, written by the agent, had defects of their own, which calls for explicit rules
of oracle design. And half of the defects left no trace in the commit history: to audit
what an agent did, one needs its transcript.

Table~\ref{tab:prompts} lists the human's prompts verbatim, up to the request to play the
game. Three kinds stand out.

\paragraph{Direction.} Five prompts set the direction, quoted here verbatim:
\begin{itemize}
  \item \emph{``I want to ask Claude to write a tiny OS with a tiny file system, with a tiny
        compiler and scripting language, all to be used in qemu/kvm or equivalent. the goal
        is that 100\% of lines of code come from Claude. Make a plan.''}
  \item \emph{``now make a plan to implement AS CC HOSTCC LD OBJCOPY and make such that we
        can build the system with generated tools only. The CC should compile the other
        tools and be self-hosted of course.''}
  \item \emph{``now install and test the self-hosted compiler inside tinyos.''}
  \item \emph{``implement in tinyos a Pokemon like game such that an AI agent later plays
        over serial port.''}
  \item \emph{``very good, it works, next step is to to make a good looking GUI like
        Pokemon Ruby on GBA.''}
\end{itemize}
The other prompts were errands around the result, such as recording and hosting a
screencast.

\paragraph{Go-aheads.} A coding agent does not run a long plan to its end on its own. It
is built to stop at natural boundaries, such as the end of a planned phase, report what it
did, and wait for the human to confirm before it goes on, even when the plan is already
approved. The human then has to nudge it forward. Here the agent ran phases 0 to 6 of the
OS without a single stop, but stopped after every phase of the toolchain.
\ngoaheads{} of the \nprompts{} prompts are such nudges, of three words or fewer:
``go'', ``proceed'', ``continue'', ``Do T3.''. Each starts the next phase of a plan the
agent wrote; none adds information. The human also approved the agent's \napprovals{}
plans.

\paragraph{Decisions.} The human answered \nquestions{} multiple-choice questions from
the agent and dismissed \ndismissed{} (Table~\ref{tab:questions}). In \nrecommended{} of
them the human picked the option the agent had marked as recommended; only one answer was
free text. One recommended answer was overturned later: at the start, the human accepted
the agent's proposal to use the existing assembler and linker as tools, and the request
for a self-hosted toolchain reversed it. The human's own technical input was two prompts. One reported that typing in
\texttt{make run} showed nothing. The other questioned whether \texttt{objcopy} was needed
at all, which removed a planned phase (T6). One goal was dropped: when asked to run the
compiler inside the OS, the agent explained that the OS has no way to load native code,
and the human moved on to the game instead.
