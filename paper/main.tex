\title{QuineOS: A Language Model Writes an Operating System and the Toolchain That Builds It}
\author{Martin Monperrus \and Claude}

\begin{document}
\maketitle

\begin{abstract}
We report on \sysname{}, an x86 operating system in which every line of code, from the
boot sector to the compiler that builds it, was written by Claude working as a coding
agent. \sysname{} boots in QEMU through its own two-stage boot loader into a 32-bit
kernel with a disk driver, a file system, a shell, a scripting language, and a compiler
to an in-kernel bytecode VM. Its build uses no third-party compiler, assembler or linker:
the agent wrote its own, and bootstrapped them until the second and third self-compiled
generations were byte-identical. The human author typed \nprompts{} prompts, \nshortprompts{}
of them three words or fewer, and wrote no code. From plan approval to a working OS with
both languages took \plantoosmin{} minutes. The toolchain took \tcactivehours{} hours of
agent activity and produced most of the \ndefects{} defects that the agent found and
fixed, most of them by running the system rather than by reading code.
\end{abstract}

\section{Introduction}\label{sec:intro}

Benchmarks for code-generating models have grown from single functions~\cite{chen2021codex}
to repository-level issue fixing~\cite{jimenez2024swebench}. Both measure changes to code
that already works. Writing a system from an empty repository is a different task. The
agent has to choose an architecture, keep it coherent over thousands of lines, and debug
failures whose only symptom may be a machine that prints nothing.

An operating system is a demanding case of this task. Unix showed that a small team can
build one that is both small and useful~\cite{ritchie1974unix}, and teaching kernels such
as xv6~\cite{cox2006xv6} show how much fits in a few thousand lines. Below the kernel
there is no runtime to report a mistake. A wrong descriptor table entry resets the
machine, and an I/O instruction with the wrong operand size corrupts the disk silently.

This paper reports what Claude built, how much the human contributed, and which defects
the agent hit. Our data are the git history of the
system\footnote{\url{https://github.com/monperrus/boot-to-claude}, commit \ospin{}.} and
the complete transcript of the Claude Code session that produced it. Every number in
this paper is computed from these two sources by a script.

\section{Goal}\label{sec:goal}

\paragraph{What we want to demonstrate.} The opening prompt stated the criterion:
\emph{``the goal is that 100\% of lines of code come from Claude.''} We make it precise
as two claims.
\begin{description}
  \item[Full AI-written stack.] No line of the system or of its build path is written by
        a human or taken from an existing project. This rules out a third-party compiler
        too: a C compiler is code, and a system built by \texttt{gcc} is partly
        \texttt{gcc}'s. The only exceptions are the emulator, which plays the role of
        the hardware, and one use of the host compiler to start the bootstrap.
  \item[Full bootstrap.] The toolchain is good enough to build itself, and the proof is
        a fixed point: compiling the compiler with itself yields the same bytes twice in
        a row. A quine is a program that prints its own source code. \sysname{} is
        named after the toolchain's equivalent: it rebuilds itself and gets the same bytes.
\end{description}

\paragraph{What we build.} A complete, if small, computing system: something that boots
on a bare (emulated) PC, stores files, and lets a user write and run programs in
languages of its own. Concretely, a boot loader, a kernel, a file system, an interactive
shell, an interpreted scripting language, and a compiled language with its virtual
machine. Then the tools that build all of it: an assembler, a C compiler and a linker.

\section{The System}\label{sec:system}

\paragraph{Boot and kernel.} The BIOS loads a 512-byte boot sector, which loads a second
stage. The second stage enables the A20 line, loads the kernel, installs a flat GDT and
switches to 32-bit protected mode. The kernel owns its GDT and an IDT that covers CPU
exceptions only. It has a free-list allocator over a fixed 1\,MB heap, VGA text and
COM1 serial output, a polled ATA PIO disk driver, and a polled PS/2 keyboard driver.

\paragraph{Deliberately single-tasking.} The kernel never enables interrupts after boot.
It has no scheduler, no paging and no user mode. The shell and both language runtimes run
in kernel context. The agent proposed this before writing any code, as the recommended
answer to its own question on how minimal the OS should be, so that the effort would go
into the file system and the languages. The human accepted.

\paragraph{Above the kernel.} \emph{tinyfs} is a flat file system with a superblock, a
free-block bitmap, a fixed inode table and 4\,KB maximum file size. Its format code is
compiled twice, once into the kernel and once into the host tool that formats the disk
image, so there is a single implementation of the on-disk format. The shell offers
\texttt{ls}, \texttt{cat}, \texttt{write}, \texttt{rm}, \texttt{run}, \texttt{build} and
\texttt{exec}. \texttt{run} executes a dynamically typed script with a tree-walking
interpreter. \texttt{build} compiles a statically scoped, integer-only C-like language to
stack bytecode, and \texttt{exec} runs it in a VM that supports recursion. A turn-based
battle game, added last, can be played from the keyboard or entirely over the serial
port, so that another agent can play it.

\paragraph{Toolchain.} \texttt{toolchain/} holds an assembler for the NASM subset the OS
uses, a compiler for a C dialect called tinyC, and a two-mode ELF32 linker. The host
\texttt{gcc} is invoked exactly once, to compile the first generation of this toolchain.

\section{How It Was Built}\label{sec:history}

The work happened in one Claude Code session using \sessionmodel{}, with
\nassistant{} model responses and \ntoolcalls{} tool calls, of which \nbash{} shell
commands and \nedit{} file writes or edits. The context window filled up and was
summarized \ncompactions{} times. Table~\ref{tab:timeline} splits the session at each
phase commit. Of the \ncommits{} commits in the repository, all but two were committed by
the agent. The other two are the initial empty commit and a ten-line Makefile target for
running QEMU with a display. The agent wrote that target in response to the human's
report that typing showed nothing, and the human ran \texttt{git commit}.

\input{gen/tab-timeline}

\paragraph{The OS in one sitting.} The agent asked four design questions, wrote a plan,
and the human approved it. Phases 0 to 6, from an empty boot sector to a compiler with a
bytecode VM, followed within \plantoosmin{} minutes, without a single further prompt.

\paragraph{The toolchain over four days.} Replacing the host tools took
\tcactivehours{} hours of agent activity, about nine times the OS. The assembler had to
grow from the instructions in four hand-written \texttt{.S} files to everything the C
compiler emits. The kernel source was first rewritten into the tinyC dialect while still
building with \texttt{gcc} (phase T3), so that each change could be checked as
behavior-preserving before the new toolchain was in the loop.

\paragraph{The fixed point.} Phase T8 compiles the toolchain three times: Stage~1 with
\texttt{gcc}, Stage~2 with Stage~1, and Stage~3 with Stage~2. Let $S_i$ be the binaries of
stage $i$. The bootstrap is accepted only when
\begin{equation}\label{eq:fixpoint}
  S_2 = S_3 \quad \text{byte for byte, for each of } \texttt{as},\ \texttt{cc},\ \texttt{ld}.
\end{equation}
Equation~\eqref{eq:fixpoint} shows that the compiler compiles itself to the same result
it was compiled to. Getting there required features the toolchain had never needed for
the kernel: variadic functions, multi-dimensional arrays, and a minimal C library
written for the purpose.

\section{What the Human Did}\label{sec:human}

Table~\ref{tab:prompts} lists every prompt. Three kinds stand out.

\paragraph{Goals.} Five prompts set the direction: the opening request, the request for
a self-hosted toolchain, a request to install the compiler inside the OS, a game an agent
could play over serial, and a graphical screen for that game. A few more were errands
around the result, such as recording and hosting a screencast.

\paragraph{Go-aheads.} \nshortprompts{} of the \nprompts{} prompts have three words or
fewer: ``go'', ``proceed'', ``Do T3.''. They start the next phase of a plan the agent
wrote. The human also approved the agent's \napprovals{} plans.

\paragraph{Decisions.} The human answered \nquestions{} multiple-choice questions from
the agent. In \nrecommended{} of them the human picked the option the agent had marked
as recommended; the remaining answer was free text naming where to host a video. The
human's own technical input was two prompts. One reported that typing in
\texttt{make run} showed nothing. The other questioned whether \texttt{objcopy} was needed
at all, which removed a planned phase (T6). One goal was dropped: when asked to run the
compiler inside the OS, the agent explained that the OS has no way to load native code,
and the human moved on to the game instead.

\section{Defects and How They Were Found}\label{sec:defects}

Commit messages list each defect fixed in their phase. Counting them gives \ndefects{}:
one in phase 3, two in phase 5, three in T1, three in T2/T4, six in T5, sixteen in T7,
eleven in T8, and one in the game. Some are missing features rather than wrong code,
such as \texttt{switch} statements not yet supported by the compiler. Three patterns
stand out.

\paragraph{Most defects were silent.} Few caused a crash. An \texttt{in}/\texttt{out}
instruction encoded without its operand-size prefix read two 16-bit words per access
instead of one, which surfaced as file system superblock corruption. The compiler's
lexer had no case for the \texttt{\textbackslash b} escape and read the backspace
character literal as the letter \texttt{b}, so every typed \texttt{b} in a shell command acted as a
backspace. In the scripting interpreter, integer addition fell through to a default
branch returning 0, so \texttt{i = i + 1} looped forever.

\paragraph{Defects hid behind other defects.} A three-operand \texttt{imul} that dropped
its immediate went unnoticed because code that wrote and read arrays used the same wrong
index formula, so the errors cancelled. It surfaced only when linker-produced code read
an array written by the kernel.

\paragraph{The system test caught what unit tests missed.} The assembler's
\texttt{.dq} directive computed its high 32 bits with a shift by 32, which x86 masks to a
shift by 0. No toolchain test used \texttt{.dq}. The boot loader's disk address packet
does, and only the full boot suite caught it. The test oracle throughout is the serial
console: QEMU runs headless, a boot-time self-test prints \texttt{SELFTEST PASS}, and a
script types shell commands into QEMU's monitor and compares the serial output against
expected files.

\section{Threats to Validity}\label{sec:threats}

Kernel and compiler code is abundant in training data, so the agent may have reproduced
known designs rather than invented them. The defect count relies on commit messages
written by the agent, so it counts what the agent chose to report. Active time is
estimated from transcript timestamps, counting gaps shorter than ten minutes; a long
build without output would be counted as idle. This is one session with one model, so
it shows that the result is possible, not how often it happens. Finally, the system runs
on QEMU only; real hardware is less forgiving.

\section{Related Work}\label{sec:related}

HumanEval~\cite{chen2021codex} measures function-level synthesis, and
SWE-bench~\cite{jimenez2024swebench} measures issue resolution in existing repositories.
\sysname{} is a single construction of a whole system from scratch. xv6~\cite{cox2006xv6}
is the natural size reference for a teaching kernel; unlike \sysname{}, it is
multi-processor and has processes and paging. seL4~\cite{klein2009sel4} shows that a
kernel can be built against a machine-checked specification. Its checks are proofs; the
checks here are tests that boot the machine. Thompson's Turing lecture on trusting
compilers~\cite{thompson1984trusting} is the classic warning that a self-hosted toolchain
is only as trustworthy as its first generation. Here that generation is built by
\texttt{gcc} from source the agent wrote.

\section{Conclusion}\label{sec:conclusion}

A language model wrote a small, single-tasking operating system, then wrote the
assembler, compiler and linker that build it, up to a byte-identical self-hosting fixed
point. The human set goals and said ``go''. The OS was the easy part. Most of the effort
and most of the defects went into the toolchain, and most defects were found by booting
the machine.
