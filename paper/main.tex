\title{QuineOS: A Language Model Writes an Operating System and the Toolchain That Builds It}
\author{Martin Monperrus \and Claude}

\begin{document}
\maketitle

\begin{abstract}
We report on \sysname{}, an x86 operating system in which every line of code, from the
boot sector to the compiler that builds it, was written by Claude working as a coding
agent. \sysname{} boots in QEMU through its own two-stage boot loader into a 32-bit
kernel with a disk driver, a file system, a shell, a scripting language, and a compiler
to an in-kernel bytecode VM. Its build uses no third-party compiler, assembler or linker:
the agent wrote its own, and bootstrapped them until the second and third self-compiled
generations were byte-identical. The human set the goals and wrote no code. From plan
approval to a working OS with both languages took \plantoosmin{} minutes. The toolchain
took \tcactivehours{} hours of agent activity and accounts for \nttoolchain{} of the
\ntproduct{} defects that the transcript shows the agent finding and fixing, half of
which no commit message mentions.
\end{abstract}

\section{Introduction}\label{sec:intro}

Power on the machine. A 512-byte boot sector loads a kernel, the kernel mounts its file
system, and a shell prompt appears. Compile a program, run it. Type \texttt{play}, and a
battle screen in the style of a Game Boy Advance lights up. No human wrote a single line
of it: not the boot sector, not the kernel, not the game, and not the assembler, C
compiler and linker that built all of them, which also built themselves. An AI did.

Coding agents are usually judged on changes to code that already works, from single
functions~\cite{chen2021codex} to repository-level issue fixing~\cite{jimenez2024swebench}.
Writing a system from an empty repository is a different task. The agent has to choose
an architecture, keep it coherent over thousands of lines, and debug failures whose only
symptom may be a machine that prints nothing. An operating system is the extreme case.
Below the kernel there is no runtime to report a mistake: a wrong descriptor table entry
resets the machine, and an I/O instruction with the wrong operand size corrupts the disk
without a word. Unix~\cite{ritchie1974unix} and xv6~\cite{cox2006xv6} show how much a
small kernel can do; they also took skilled people to write.

There are precedents for agents building large systems from nothing. A team of 16 Claude
agents wrote a C compiler that builds Linux, but it relies on GCC's assembler and
linker~\cite{carlini2026ccc}. Hundreds of agents built a web browser in a
week~\cite{lin2026scaling}. A month before this work, Claude Fable 5 wrote the core of an
NT-style kernel in Rust, with a scheduler and a memory manager, that boots in
QEMU~\cite{suiche2026ntoskrnl}. All of them are compiled by existing, human-written
compilers (GCC, \texttt{rustc}), so every instruction that runs was chosen by a code
generator no agent wrote. To the best of our knowledge, no one has reported a
bootstrapped operating system written by an AI: one where the AI wrote not only the OS
but also the assembler, compiler and linker that build it, where that toolchain compiles
itself to a byte-identical fixed point, and where it is the only toolchain that ever
compiles the OS. \sysname{} is such a system.

\paragraph{Methodology.} One human gave one Claude Code agent (\sessionmodel{}) a goal
and an empty repository, and let it work in a single session. The human set goals,
answered the agent's questions and said ``go'', but wrote no code. We study two
artifacts: the git history of the
system\footnote{\url{https://github.com/monperrus/boot-to-claude}, commit \ospin{}.} and
the complete transcript of the
session,\footnote{\url{https://github.com/monperrus/boot-to-claude-paper}} with every
prompt, model response, tool call and tool output. Every number in this paper is computed from these two sources by a script,
including how often the agent ran each oracle and how often the oracle said no.

\paragraph{Results.} \sysname{} boots through its own boot loader into a kernel with a
file system, a shell, a scripting language and a compiler to bytecode. Its assembler, C
compiler and linker were written by the agent and compile themselves to byte-identical
binaries. From plan approval, the OS with both languages took \plantoosmin{} minutes;
the toolchain took \tcactivehours{} hours of agent activity. The agent ran its
scripted oracles \noraclesruns{} times and saw \noraclesfailed{} failures, most of them
while switching the build to its own toolchain. The transcript records \ntproduct{}
defects found and fixed in the system, \nttoolchain{} of them in the toolchain; only
\ntreported{} appear in a commit message.

\paragraph{A game for an AI player.} The last request was for fun: a Pokémon-like game
that an AI agent could play over the serial port. Claude wrote \emph{Tiny Monsters}, then
a graphical battle screen in the style of the Game Boy Advance games, drawn pixel by
pixel by its own VGA driver, and then played the game itself, \playruns{} runs in five
minutes. Anthropic has shown Claude playing Pokémon Red~\cite{techcrunch2025pokemon};
here Claude also wrote the game, the operating system under it, and the compiler that
built both.

\paragraph{Contributions.}
\begin{itemize}
  \item \textbf{The first bootstrapped operating system written by an AI}, to the best of
        our knowledge. \sysname{} has its own boot loader, kernel, file system, shell and
        two languages, and its own assembler, C compiler and linker, which compile
        themselves to a byte-identical fixed point and are the only tools that build the
        OS. No line of the stack was written by a human.
  \item \textbf{One agent, one session, no human code.} Where comparable systems used
        teams of 16 to hundreds of agents~\cite{carlini2026ccc,lin2026scaling}, a single
        agent wrote \sysname{}. The OS with both languages took \plantoosmin{} minutes
        from plan approval; the full toolchain, \tcactivehours{} hours of agent activity.
  \item \textbf{The oracle, not the code, is what makes it possible.} We show from the
        transcript that the agent was only as good as its oracles: it ran them
        \noraclesruns{} times, they rejected its work \noraclesfailed{} times, and the
        most telling defects were silent ones that only an oracle booting the whole
        machine caught.
  \item \textbf{A fully transparent open-science package.} We release the system's
        source and history, the complete transcript of the session that built it, with
        every prompt, model response, tool call and tool output, and the scripts that
        recompute every number, table and figure in this paper from them. Anyone can
        check every claim we make, down to the individual tool call: the phases,
        prompts, oracle runs and defects in this paper are hyperlinks into the rendered
        transcript.\footnote{\url{\siteurl}}
  \item \textbf{A game written by an AI, for an AI}, on a stack written by an AI from the
        boot sector up.
\end{itemize}

\section{Goal}\label{sec:goal}

\paragraph{Claims.} We study total AI authorship of a computing system: every line of
code, in the system and in everything that builds it, produced by an AI coding agent.
The agent in this study is Claude, but the model is incidental; the question is whether
total authorship is achievable by an AI agent at all. We decompose it into two claims.
\begin{description}
  \item[Full AI-written stack.] No line of the system or of its build path is written by
        a human or taken from an existing project. This rules out a third-party compiler
        too: a C compiler is code, and a system built by \texttt{gcc} is partly
        \texttt{gcc}'s. The only exceptions are the emulator, which plays the role of
        the hardware, and one use of the host compiler to start the bootstrap.
  \item[Full bootstrap.] The AI-written toolchain builds the OS and builds itself, and
        the proof is a fixed point: compiling the compiler with itself yields the same
        bytes twice in a row. A quine is a program that prints its own source code.
        \sysname{} is named after the toolchain's equivalent: it rebuilds itself and gets
        the same bytes.
\end{description}

\paragraph{Rationale for the bootstrap.} An OS whose source an AI wrote but which \texttt{gcc}
compiles is still a joint work: every machine instruction that runs was chosen by a code
generator written by people. The bootstrap removes that dependency. The host compiler is
used once, to produce a first binary of the AI's compiler; from then on the AI's compiler
compiles itself, and the fixed point shows that the result no longer depends on the host
compiler's code generation. The bootstrap is also a strong test in its own right: a
compiler that compiles its own source correctly has to handle a real, large C program
that the AI did not write for the purpose of testing it.

\paragraph{Two compounding difficulties.} The two claims stack two hard problems. The first is
the operating system: code that runs on bare hardware, with no runtime underneath, where
a mistake resets the machine or corrupts data without a word. The second is a compiler
strong enough to compile both that operating system and itself. Building a C compiler is
hard even with abundant resources: Anthropic's team of 16 agents spent about \$20{,}000
on a C compiler that builds Linux, and still relies on GCC's assembler and
linker~\cite{carlini2026ccc}. \sysname{} needs a much smaller dialect of C, but also an
assembler and a linker, and no external tool to fall back on. The two difficulties
compound. When the OS misbehaves, the cause may be in the OS or in the compiler that
built it, and the symptom looks the same. An \texttt{in} instruction encoded without its
operand-size prefix, for example, showed up as a corrupted file system
(Section~\ref{sec:defectlist}).

\paragraph{Scope.} The target is a complete, if small, computing system: one that boots
on a bare (emulated) PC, stores files, and lets a user write and run programs in
languages of its own. Concretely, a boot loader, a kernel, a file system, an interactive
shell, an interpreted scripting language, and a compiled language with its virtual
machine. Then the tools that build all of it: an assembler, a C compiler and a linker.

\section{\sysname}\label{sec:system}

\paragraph{Boot and kernel.} The BIOS loads a 512-byte boot sector, which loads a second
stage. The second stage enables the A20 line, loads the kernel, installs a flat GDT and
switches to 32-bit protected mode. The kernel owns its GDT and an IDT that covers CPU
exceptions only. It has a free-list allocator over a fixed 1\,MB heap, VGA text and
COM1 serial output, a polled ATA PIO disk driver, and a polled PS/2 keyboard driver.

\paragraph{Deliberately single-tasking.} The kernel never enables interrupts after boot.
It has no scheduler, no paging and no user mode. The shell and both language runtimes run
in kernel context. The agent proposed this before writing any code, as the recommended
answer to its own question on how minimal the OS should be, so that the effort would go
into the file system and the languages. The human accepted.

\paragraph{Above the kernel.} \emph{tinyfs} is a flat file system with a superblock, a
free-block bitmap, a fixed inode table and 4\,KB maximum file size. Its format code is
compiled twice, once into the kernel and once into the host tool that formats the disk
image, so there is a single implementation of the on-disk format. The shell offers
\texttt{ls}, \texttt{cat}, \texttt{write}, \texttt{rm}, \texttt{run}, \texttt{build} and
\texttt{exec}. \texttt{run} executes a dynamically typed script with a tree-walking
interpreter. \texttt{build} compiles a statically scoped, integer-only C-like language to
stack bytecode, and \texttt{exec} runs it in a VM that supports recursion. The shell's
\texttt{play} command starts a game, described in Section~\ref{sec:game}.

\paragraph{The \sysname{} toolchain.} Three tools replace \texttt{nasm}, \texttt{gcc},
\texttt{ld} and \texttt{objcopy}:
\begin{itemize}
  \item an \emph{assembler} for the subset of NASM syntax that the OS's assembly files
        and the compiler's output use, with no macro preprocessor. It writes either a
        flat binary (the boot sectors) or an ELF32 relocatable object;
  \item a \emph{C compiler} for tinyC, a C dialect scoped to what the code base needs:
        \texttt{\#include} and constant \texttt{\#define} only, structs, unions, enums
        and function pointers, no type wider than 32 bits. It emits assembly text for the
        assembler, either freestanding for the kernel or as a static Linux program that
        calls the kernel directly through system calls;
  \item a \emph{linker} that merges ELF32 objects, applies the two x86 relocation types
        the assembler produces, and writes either the flat kernel image or a static
        Linux executable. Writing the flat image itself made \texttt{objcopy}
        unnecessary.
\end{itemize}
A minimal C library (unbuffered \texttt{FILE} I/O, a bump allocator, a subset of
\texttt{printf}) lets the toolchain's own source, which uses ordinary libc calls, be
compiled by the toolchain. Table~\ref{tab:size} gives the size of each part.

\paragraph{Bootstrap path.} The toolchain is written in C, so its very first binary has
to come from a compiler that already exists. The host C compiler (\texttt{gcc} by
default, any C compiler will do) is used exactly once, to build Stage~1 of the
toolchain from its source. Stage~1 then compiles the same source into Stage~2, and
Stage~2 compiles it again into Stage~3. Let $S_i$ be the binaries of stage $i$. The
bootstrap is accepted only when
\begin{equation}\label{eq:fixpoint}
  S_2 = S_3 \quad \text{byte for byte, for each of } \texttt{as},\ \texttt{cc},\ \texttt{ld}.
\end{equation}
Equation~\eqref{eq:fixpoint} shows that the compiler compiles itself to the same result
it was compiled to, so the bytes of Stage~2 come from the toolchain's own code
generator, not from the host compiler's. Stage~2 then
builds the boot loader, the kernel and the disk-image tool; the host compiler never
compiles any of them. The emulator, \texttt{qemu-system-i386}, stays external: it is the
machine \sysname{} runs on, not part of what builds it.

\section{Tiny Monsters: A Game Made for an AI Player}\label{sec:game}

The last thing the human asked for was not infrastructure but fun: \emph{``implement in
tinyos a Pokemon like game such that an AI agent later plays over serial port.''} The
result, \emph{Tiny Monsters}, is the most visible demonstration of the full AI-written
stack. Every pixel in Figure~\ref{fig:battle} is drawn by code Claude wrote, compiled by
the compiler Claude wrote, on a kernel Claude wrote, and the game was first played by
Claude.

\paragraph{Rules.} Three species, Emberpup, Aqualing and Leafling, one per type in a
rock-paper-scissors cycle: Fire beats Grass, Grass beats Water, Water beats Fire. A move
with the type advantage does 1.5 times its damage, one against it half. The player picks
a starter and meets wild monsters whose HP grows with each win. HP does not regenerate,
and five wins make the player Champion.

\paragraph{Made for a machine player.} Until then the kernel only read the keyboard; the
serial port was output only. The agent added serial input and made the shell and the
game poll both sources (\inputlines{} lines in \texttt{input.c}), so a human at the
keyboard and a program on the serial line can drive the same session interchangeably.
The game speaks a plain text protocol: it prints the screen as text, and reads a digit,
\texttt{run} or \texttt{quit}. Asked to play for five minutes, the agent connected a
script to QEMU's serial socket and played \playruns{} runs in \playseconds{} seconds,
restarting after each faint. Playing found a \defect{D-C09-01}{real bug}: the random move
picker took a modulo of a 32-bit value with the sign bit set, which \sysname{}'s compiler
only supports as signed division, and read a garbage move name with absurd damage.

\paragraph{A graphical battle screen.} Asked next for \emph{``a good looking GUI like
Pokemon Ruby on GBA''}, the agent wrote a driver for VGA mode 13h (320$\times$200, 256
colors) that programs the video card's registers directly, without BIOS calls
(\vgadriver{} lines), and a bitmap font of its own design (\fontlines{} lines). The three
monsters are not images: \texttt{sprites.c} draws them from filled circles, ellipses and
triangles in \gamesprites{} lines. The battle scene, with sky, ground, platforms, HP bars
and a dialogue box, takes \gamegui{} lines on top of the \gamerules{} lines of game
logic. The graphics are purely additive: the text sent over serial is byte for byte the
same, so the machine player sees no difference. Returning to the shell restores text
mode, which took a debugging session of its own because \defect{D-C09-05}{mode 13h
overwrites the video memory plane} where the text font lives.

\paragraph{Screencasts.} The agent recorded both versions as videos: the five-minute
serial session, and the graphical battle screen from which Figure~\ref{fig:battle} is
taken. For the second, it drove the game with emulated keystrokes and captured QEMU's
frame buffer, after fixing \defect{D-C10-06}{two} \defect{D-C10-07}{bugs} in its own
capture script along the way.

\section{How It Was Built}\label{sec:history}

The work happened in one Claude Code session using \sessionmodel{}, with
\nassistant{} model responses and \ntoolcalls{} tool calls, of which \nbash{} shell
commands and \nedit{} file writes or edits. The context window filled up and was
summarized \ncompactions{} times. Table~\ref{tab:timeline} splits the session at each
phase commit. Of the \ncommits{} commits in the repository, all but two were committed by
the agent. The other two are the initial empty commit and a ten-line Makefile target for
running QEMU with a display. The agent wrote that target in response to the human's
report that typing showed nothing, and the human ran \texttt{git commit}.

\paragraph{The OS in one sitting.} The agent asked four design questions, wrote a plan,
and the human approved it. Phases 0 to 6, from an empty boot sector to a compiler with a
bytecode VM, followed within \plantoosmin{} minutes, without a single further prompt.

\paragraph{The toolchain over four days.} Replacing the host tools took
\tcactivehours{} hours of agent activity, about nine times the OS. The assembler had to
grow from the instructions in four hand-written \texttt{.S} files to everything the C
compiler emits. The kernel source was first rewritten into the tinyC dialect while still
building with \texttt{gcc} (phase T3), so that each change could be checked as
behavior-preserving before the new toolchain was in the loop.

\paragraph{The fixed point.} Phase T8 implemented the bootstrap path and reached
Equation~\eqref{eq:fixpoint}. Compiling the toolchain with itself required features it
had never needed for the kernel: variadic functions, multi-dimensional arrays, and the
minimal C library.

\section{Oracles: How the Agent Knew It Was Right}\label{sec:defects}

A coding agent is as strong as its oracle. The agent proposes a change, the oracle
judges it, and the agent iterates until the oracle agrees. Nothing in this loop needs a
human, but everything depends on the oracle: a weak one lets defects through, a missing
one leaves the agent guessing. \sysname{} had strong oracles, listed in
Table~\ref{tab:oracles}, and the agent consulted them constantly: it ran the four
scripted ones \noraclesruns{} times, and \noraclesfailed{} of those runs failed.

\input{gen/tab-oracles}

\paragraph{One observation channel.} Every oracle that runs the OS reads the same thing:
the serial console. The kernel prints everything it shows on screen to COM1 as well, the
CPU exception handlers print the faulting vector before halting, and QEMU runs headless
with its serial port captured to a file. A crash, a hang and a wrong answer all become
text the agent can read. The agent built this channel in phase 0, before there was
anything to test, and kept it for six days.

\paragraph{Binary verdicts.} Each scripted oracle ends with one line, \texttt{PASS} or
\texttt{FAIL}. There is nothing to interpret. When a
run produces neither, because the machine hung until the timeout or the build broke
first, the absence of \texttt{PASS} is itself the failure.

\paragraph{End to end.} The OS system test boots the real boot loader and kernel built by
the toolchain under test, and drives them as a user would. Any defect anywhere on that
path, in the assembler's encoding, the compiler's code generator or the linker's
relocations, shows up as a wrong line on the serial console. This is what made the
toolchain safe to replace: the OS itself is the largest test program the toolchain has.

\paragraph{Fast and slow.} The toolchain tests run \ntoolchainfixtures{} small programs on
the host in seconds; the OS test boots a machine. The agent ran them
\ntoolchaintestruns{} and \nostestruns{} times respectively, iterating on the fast oracle
and confirming on the slow one.

\paragraph{References while they exist, a fixed point afterwards.} During the transition
the old tools were still available, and the agent used them as a differential oracle.
The kernel was first rewritten into the tinyC dialect while still building with
\texttt{gcc}, so the OS test could confirm each rewrite before the new compiler was in
the loop. The linker's flat output was compared byte for byte with \texttt{objcopy}'s.
Once the old tools were gone, Equation~\eqref{eq:fixpoint} took over: the bootstrap
checks the toolchain against itself and needs no reference at all.

\paragraph{The oracle grows.} When the switch-over to the new toolchain surfaced a
defect, the agent added a regression test for its class: the switch-over commit adds ten
toolchain tests, one per bug class. \ntsevenfailed{} of the \noraclesfailed{} failing
oracle runs happened in that phase, which is where the oracles earned their keep.

\paragraph{Where the oracles are weaker.} Battle outcomes depend on a random number
generator, so the game tests accept any end state and only check the flow. The graphical
screen has no scripted oracle at all: the agent judged it by looking at frame-buffer
dumps (\nimagereads{} images), the weakest check in the table.

\subsection{Defects}\label{sec:defectlist}

\paragraph{Method.} Commit messages report the defects the agent chose to mention. To
see all of them, we cut the transcript into ten chunks at phase boundaries and had ten
annotator agents list every defect the agent encountered: what was wrong, the tool call
whose output first showed it, the edits that fixed it, the check that confirmed the fix,
and the commit message that reports it, if any. Each record had to quote its evidence
verbatim. A script then checked every cited tool call against the transcript and every
quote against the chunk; two records needed a correction and one duplicate across a
chunk boundary was merged, each kept in a committed file with its reason. We checked a
random 10\% sample against the transcript output it cites, and checked that every defect
named in a commit message has a record.

\paragraph{Results.} The transcript holds \ntdefects{} defects: \ntproduct{} in
\sysname{} itself, \ntoracle{} in the oracle tooling, and \ntenv{} in the environment
(Table~\ref{tab:defects}). Only \ntreported{} of the \ntproduct{} product defects are
reported in a commit message; the other \ntunreported{} were found and fixed between
commits and left no trace in the history. The toolchain accounts for \nttoolchain{} of
the \ntproduct{}, the C compiler alone for \ntcc{}: building a compiler strong enough
was the harder half of the task. \ntmultiattempt{} defects took more than one failing
check to fix, up to \ntmaxattempts{}. Some are missing features rather than wrong code,
such as \defect{D-C05-02}{\texttt{switch} statements} not yet supported by the compiler.

\input{gen/tab-defects}

\paragraph{What revealed them.} \ntbuildrevealed{} product defects showed up at build
time, mostly the compiler rejecting C it did not yet support. \ntbootrevealed{} were
caught by an oracle that boots the machine, and \ntsilent{} had a silent symptom: wrong
output, a hang, corrupted data or a wrong picture, with no error message. \ntcodereading{}
were found by the agent reading its own code, typically while investigating a nearby
failure. Three patterns show why the end-to-end oracles mattered.

\paragraph{Many defects were silent.} Few caused a crash. An
\defect{D-C06-04}{\texttt{in}/\texttt{out} instruction} encoded without its operand-size
prefix read two 16-bit words per access instead of one, which surfaced as file system
superblock corruption. The compiler's lexer had \defect{D-C06-13}{no case for the
\texttt{\textbackslash b} escape} and read the backspace character literal as the letter
\texttt{b}, so every typed \texttt{b} in a shell command acted as a backspace. In the
scripting interpreter, \defect{D-C01-08}{integer addition} fell through to a default
branch returning 0, so \texttt{i = i + 1} looped forever.

\paragraph{Defects hid behind other defects.} A \defect{D-C04-12}{three-operand
\texttt{imul}} that dropped its immediate went unnoticed because code that wrote and read arrays used the same wrong
index formula, so the errors cancelled. It surfaced only when linker-produced code read
an array written by the kernel.

\paragraph{The system test caught what unit tests missed.} The assembler's
\defect{D-C08-08}{\texttt{.dq} directive} computed its high 32 bits with a shift by 32, which x86 masks to a
shift by 0. No toolchain test used \texttt{.dq}. The boot loader's disk address packet
does, and only the OS system test caught it.

\subsection{Defects in the oracle loop}\label{sec:oracledefects}

The oracles are code too, written by the same agent, and \ntoracle{} of the defects were
in them. They differ in nature from product defects: a product defect makes the oracle
say no, while an oracle defect makes it say the wrong thing, or nothing. Three kinds
appear.

\paragraph{Oracles that could not fail.} The toolchain test runner
\defect{D-C03-18}{had no expected exit code} for one fixture, so that test was silently
skipped. The \defect{D-C04-13}{pointer test kept passing} with the broken three-operand
\texttt{imul}, because it wrote and read arrays with the same wrong index formula. Worse,
\defect{D-C04-17}{ad-hoc verification commands} printed success lines such as
\texttt{IDENTICAL} after a step had already failed, and misled the diagnosis. A
false \texttt{PASS} is the most dangerous output an oracle can produce, because the agent
trusts it.

\paragraph{Oracles that could not observe.} A \defect{D-C09-03}{QEMU serial socket} in
\texttt{server,nowait} mode discards everything the guest prints before a client
connects, so a script waiting for the boot banner timed out on a healthy machine. A
\defect{D-C10-06}{screencast recorder} assumed 320$\times$200 frames where QEMU produces 640$\times$400, and
the agent first blamed a torn file read. Each time, the agent had to debug its
instrument before it could trust it again.

\paragraph{Oracles that killed themselves.} \defect{D-C10-05}{Several commands} killed
leftover QEMU processes with \texttt{pkill -f} and a pattern that also matched the command line of
the shell running it, so the shell died and the test never ran. The symptom, a
silent exit code, looks exactly like a failing system.

\section{Threats to Validity}\label{sec:threats}

The defect analysis relies on annotator agents reading the transcript. They may have
missed defects or misjudged a cause; we mitigated this with mandatory verbatim
evidence, an automatic check of every quote and tool call, a coverage check against
the commit messages, and a manual check of a random sample. Oracle verdicts are read from the transcript by matching each
script's \texttt{PASS} and \texttt{FAIL} lines. Active time is
estimated from transcript timestamps, counting gaps shorter than ten minutes; a long
build without output would be counted as idle. This is one session with one model, so
it shows that the result is possible, not how often it happens. Finally, the system runs
on QEMU only; real hardware is less forgiving.

\section{Related Work}\label{sec:related}

\paragraph{Complex systems built by coding agents.} Since 2025, practitioners have
reported coding agents building systems far beyond single features, mostly in blog posts
rather than papers. The closest to \sysname{} is Anthropic's C compiler~\cite{carlini2026ccc}:
16 parallel Claude Opus 4.6 agents, nearly 2{,}000 sessions and about \$20{,}000 produced a
100{,}000-line Rust compiler that builds Linux 6.9 for three architectures. It has no
assembler or linker of its own and calls GCC for 16-bit x86 code, whereas \sysname{} owns
its assembler, compiler and linker and reaches a self-hosting fixed point, at a far
smaller scale. Its author used GCC as the oracle, compiling a random part of the kernel
with GCC and the rest with the new compiler to locate failures. Cursor ran hundreds of
agents for about a week in a planner, worker and judge hierarchy to build FastRender, a
web browser of over a million lines~\cite{lin2026scaling}. Huntley ran Claude in a loop
with a single prompt for three months and obtained \emph{cursed}, a programming language
with an LLVM back end~\cite{huntley2025cursed}. Stenström built JustHTML, an HTML5 parser
that passes the 9{,}200 tests of html5lib-tests, and states the lesson this paper also
draws: \emph{``you need a way for them to understand their own progress. A complete test
suite is perfect for that''}~\cite{stenstrom2025justhtml}. Closest in domain, Suiche
reports that Claude Fable 5 wrote the core of \texttt{ntoskrnl-rs}, an NT-style x86-64
kernel in Rust that boots in QEMU and passes its self-tests, in 38 minutes of active
work, in June 2026~\cite{suiche2026ntoskrnl}. As a kernel it is more ambitious than
\sysname{}'s: it has a scheduler, a memory manager with page tables, and interrupt-driven
timers, and later work ran unmodified Windows drivers and programs. But it is a Rust
project compiled by \texttt{rustc}, and its core has no file system, shell or user
programs. Three things set \sysname{} apart: one agent in one
session, with no multi-agent orchestration; a whole stack from boot sector to a
self-hosted toolchain with no third-party compiler left in the build; and a complete
transcript from which every number here is computed.

\paragraph{Benchmarks for building from scratch.} HumanEval~\cite{chen2021codex} measures
function-level synthesis, and SWE-bench~\cite{jimenez2024swebench} measures issue
resolution in existing repositories. Commit0~\cite{zhao2025commit0} asks agents to
implement 54 Python libraries from a specification and unit tests. ProjectEval~\cite{liu2025projecteval}
and ProjDevBench~\cite{lu2026projdevbench} evaluate whole projects generated from natural
language requirements. In all of them the oracle is given to the agent. In \sysname{} the
agent wrote its oracles too (Section~\ref{sec:defects}).

\paragraph{Agents that play games.} In Claude Plays Pokémon, Claude plays Pokémon Red
through an emulator, reading the screen and pressing buttons~\cite{techcrunch2025pokemon}.
Tiny Monsters reverses the setup: the agent wrote the game, the OS under it and the
toolchain that built both, and designed a text interface over the serial port so that an
agent can play without reading pixels.

\paragraph{Trusting a self-hosted toolchain.} Thompson's Turing lecture on trusting
compilers~\cite{thompson1984trusting} is the classic warning that a self-hosted toolchain
is only as trustworthy as its first generation. Here that generation is built by the host
C compiler from source the agent wrote.

\section{Conclusion}\label{sec:conclusion}

A language model wrote a small, single-tasking operating system, then wrote the
assembler, compiler and linker that build it, up to a byte-identical self-hosting fixed
point. The human set goals and said ``go''. The OS was the easy part. Most of the effort
and most of the defects went into the toolchain, and most defects were found by booting
the machine.
